# CyberShield v1.1 — Infrastructure Location Intelligence (Design Spec)

> **STATUS: DESIGN SPECIFICATION ONLY.**
> This document describes *future* v1.1 work. It changes no application code,
> schema, frontend, dependency, or configuration. It has no implementation
> intent beyond recording the design.
>
> CyberShield **v1 remains unchanged**. Current v1 commit:
> `9b0c31b` — `feat: release CyberShield v1`
>
> This document is based on the completed infrastructure-location audit of the
> v1 codebase and on the existing CyberShield architecture
> (see [`architecture.md`](architecture.md)). It records only capabilities the
> audit actually found; it does not invent providers, fields, or behaviors.

---

## 1. Problem statement

A security assessment of a domain benefits from knowing *where the site is
hosted*: which network (ASN) serves the IP, which hosting organization operates
it, and in which country/region that infrastructure sits. Today CyberShield v1
already resolves the target's IPv4/IPv6 addresses (DNS module) and records
registrant metadata (WHOIS), but it has **no ASN, ISP, hosting-organization,
network/CIDR, country-of-hosting or coordinate data** anywhere in the pipeline
or UI. Anyone wanting that context must query a third-party service manually.

v1.1 adds a small, purely **informational** infrastructure-intelligence
capability: **IP → ASN → Hosting Organization → Country → Region**.

Location is context for the analyst. It is explicitly **not** a security signal:
it must never affect the Trust Score, the verdict, module penalties, or finding
severity. Ordinary IP geolocation does **not** establish the physical location
or identity of any person behind the scanned infrastructure.

## 2. Goals

- Provide target infrastructure location context in the scan result:
  **IP → ASN → hosting organization → country → region**.
- Surface it on the **Dashboard** and the **Report** page as an
  `InfrastructureCard`.
- Be **provider-backed** (an external ASN/geolocation service behind an adapter)
  and **cached by IP** to control rate limits and latency.
- Degrade gracefully: unavailable/late/malformed provider data becomes an
  `unavailable` state with **zero effect on scoring or findings**.
- Clearly label *target infrastructure location* vs *threat infrastructure
  location* and **never** present either as "attacker location".

## 3. Non-goals (v1.1)

- ❌ **No map.** No map library, no tile provider, no map component.
- ❌ No city-level precision beyond what a licensed provider reliably supplies;
  v1.1 shows country → region; coordinates are out of scope unless explicitly
  reconsidered in a later release.
- ❌ No "attacker location", "attacker attribution", or identity claims.
- ❌ No scoring impact: Trust Score, Risk Engine, verdict, module penalties and
  finding severity are untouched.
- ❌ No new persistence columns or migration (data lives in the existing
  `analysis_json` blob).
- ❌ No new threat-intelligence provider; the feature is orthogonal to
  threatintel scoring.
- ❌ No user accounts, no alerting, no historical trend views.
- ❌ No changes to any v1 module, schema, or UI contract except purely additive
  new surfaces.

## 4. Data flow

```
Domain/URL
   ↓ (ScanManager stage 0: url_analysis — unchanged)
   ↓ (ScanManager stage 1, concurrent: existing domain modules — unchanged)
   Domain
   ↓
New: Infrastructure module (TARGET_DOMAIN, runs concurrently in stage 1)
   ↓
IP extraction: first A record (+ AAAA) — ALREADY resolved by DNS module;
   the infrastructure module resolves its own copy independently
   (modules never call each other — ScanManager owns coordination)
   ↓
Provider adapter lookup (per resolved IP) — external, optional, env-keyed
   ↓
InfrastructureProfile (new schema)  ──►  ModuleResult.details["infrastructure"]
   ↓
AnalysisResponse.modules[]           (no weight, no scoring path)
   ↓
API /scan, /history/{scan_id}        (details persist in analysis_json)
   ↓
Frontend: InfrastructureCard on Dashboard + Report page
```

Key invariant: the infrastructure module produces a `ModuleResult` exactly like
every other module (`backend/app/modules/base.py`), but it is **absent from
`MODULE_WEIGHTS`** (`backend/app/risk_engine/weights.py`), which is the single
mechanism that guarantees zero scoring impact (unweighted modules are skipped by
the scorer).

## 5. Proposed backend architecture

- New package `backend/app/modules/infrastructure/` containing:
  - `scanner.py` — entry `scan_infrastructure_module(domain)` returning
    `ModuleResult` (mirrors `blacklist/scanner.py` structure).
  - `service.py` — composition: resolve IPs → adapter lookup (per IP) →
    normalize → `ModuleResult`; provider injection point for tests.
  - `models.py` — `InfrastructureProfile` (see §7).
  - `rules.py` — module name constants only. **No penalties, no findings of
    severity beyond `info`, no score reduction.**
  - `adapter.py` (or `adapters/`) — the provider boundary (see §6).
- Registry: append an `InfrastructureScanner` (a `BaseModule` subclass,
  `target_kind=TARGET_DOMAIN`) to `MODULE_REGISTRY`
  (`backend/app/modules/registry.py:180-192`). The ScanManager then runs it
  automatically in the concurrent stage-1 batch with no orchestrator changes.
- Risk Engine: **no change**. No entry is added to `MODULE_WEIGHTS`; the
  scorer's weight-based inclusion rule (`risk_engine/scorer.py`) already skips
  it, so score and confidence aggregation are untouched. If the weight dict is
  ever edited, an explicit `"infrastructure": 0.0` comment entry keeps intent
  visible.
- Persistence: no change — `ModuleResult.details` is free-form JSON
  (`schemas/module_result.py`), and the whole response is stored in
  `analysis_json` (`services/history_service.py`).
- Optional parity endpoint `GET /infrastructure/{domain}` in
  `backend/app/api/routes/` mounted in `main.py`, following the existing
  per-module route pattern (e.g. `api/routes/dns.py`). Convenience only; the
  scan pipeline does not depend on it.

## 6. Provider adapter boundary

The provider must be **replaceable without changing the rest of the
application**. Follow the existing threat-intel adapter contract
(`backend/app/modules/threatintel/adapters/base.py`) as the template.

Required interface (design; not implemented):

```python
class InfrastructureAdapter(ABC):
    def is_configurable(self) -> bool: ...          # key/env present?
    def lookup(self, ip_address: str) -> InfrastructureData | None
        # Never raises for transport/payload problems:
        # failures return None (or a typed Unavailable) so the module
        # degrades to an informational "unavailable" state.
```

`InfrastructureData` fields the adapter must be able to supply (all nullable):

- `ip` — the queried IP (echoed for display/source associations)
- `asn` — e.g. `"AS15169"`
- `asn_organization` — e.g. `"Google LLC"`
- `isp` — ISP name if the provider supplies it distinctly
- `hosting_provider` — hosting organization if distinct from ISP
- `network` — CIDR block, e.g. `"142.250.0.0/15"`
- `reverse_dns` — PTR hostname if the provider supplies it
- `country` — country name (e.g. `"United States"`)
- `country_code` — ISO 3166-1 alpha-2 (e.g. `"US"`)
- `region` — state/province-level name, **only when provider-guaranteed**
- `source` — provider slug for provenance

Provider selection is **explicitly deferred** (§23 lists only candidates).
Every provider response is treated as untrusted data and normalized/validated
inside the adapter; unknown fields are dropped, `None` stays `None`.

If a future provider also exposes per-IP threat findings (e.g. a reputation
feed), those go through the existing threatintel signal path — never through
this informational module.

## 7. Proposed infrastructure data model

```python
class InfrastructureProfile(BaseModel):
    """Informational hosting/location context for a resolved IP.

    Approximate by nature: IP geolocation locates the network endpoint,
    not a person. This profile is display context only; it is excluded
    from risk scoring by construction (no weight in MODULE_WEIGHTS).
    """

    domain: str
    ip_address: str | None = None           # first A record queried
    asn: str | None = None
    asn_organization: str | None = None
    isp: str | None = None
    hosting_provider: str | None = None
    network: str | None = None              # CIDR
    reverse_dns: str | None = None
    country: str | None = None
    country_code: str | None = None
    region: str | None = None
    source: str | None = None               # provider slug
    status: Literal["available", "unavailable"] = "unavailable"
    reason: UnavailableReason = "network"   # reuse threatintel reason codes
    timestamp: str = ...                    # UTC ISO-8601
```

Notes:

- Lives either as its own `backend/app/schemas/infrastructure.py` or nested in
  the module package; it reaches clients via
  `ModuleResult.details["infrastructure"]`.
- `ModuleResult.status` follows the existing `ok/warning/critical/error`
  grammar (`score_to_status`); an unavailable provider is **`ok` with a
  high score and no findings** — same philosophy as the v1 WHOIS-unavailable
  rule: a missing data point is never a finding.
- No coordinates, no timezone in the v1.1 model (see §3 and §24).
- No top-level `AnalysisResponse.infrastructure` field required; module
  `details` is sufficient and keeps v1 response shape intact. (Could be added
  later as sugar without breaking clients.)

## 8. Caching strategy

Design only — no implementation.

- **Cache key:** the resolved IP address (string), namespace-prefixed to avoid
  collisions, e.g. `infra:{ip}`. IPv4 and IPv6 distinct keys.
- **Store:** in-process dict/`functools.lru_cache`-style bounded cache is
  sufficient for the single-user v1 deployment model (v1 has no auth, no
  multi-tenant); use a TTL + max-entries cap. A future Redis/sqlite cache is
  not needed for v1.1.
- **TTL:** configurable, default ~24 h for ASN/network data (changes rarely)
  and ~24–72 h for country/region (stable). A single `INFRASTRUCTURE_CACHE_TTL`
  env default is acceptable for v1.1; do not cache `unavailable` results for
  longer than a few minutes (default ~5 min) so a transient provider outage
  does not poison the cache.
- **Provider failures:** never cache fatal-permanent states (bad config);
  short-TTL cache transient failures so repeated scans of the same popular IP
  do not hammer the provider during an outage.
- **Stale data behavior:** expired entries are dropped and re-queried; read
  through always returns fresh-or-failed, never fabricated values. If a future
  release adds offline staleness serving, it must keep the `source` +
  `timestamp` labels visible in the UI.
- **Privacy/security:** cache holds only public routing data (ASN, network,
  country) derived from public IPs already shown in scan results; no
  personally identifying data. The cache must not log query IPs beyond the
  scan itself (append-only scan history already records resolved IPs as print
  output of the DNS module).

## 9. API / schema considerations

- `GET /scan/{target}` and `GET /history/{scan_id}`: the infrastructure
  `ModuleResult` appears automatically in `modules[]`; no response-shape change
  for existing clients.
- `GET /infrastructure/{domain}` (optional parity endpoint): returns the
  `ModuleResult` for the infrastructure module only.
- Exports:
  - JSON — flows through automatically (`modules/reporting/json.py` dumps the
    whole model).
  - CSV/PDF — require explicit blocks mirroring the existing `threatintel`
    sections (`modules/reporting/csv.py`, `modules/reporting/pdf.py`).
- No database migration: `Scan.analysis_json` already stores full module
  details.
- New config keys (all optional, all env-only, documented in `.env.example`):
  `INFRASTRUCTURE_ENABLED`, `INFRASTRUCTURE_PROVIDER`, `INFRASTRUCTURE_API_KEY`,
  `INFRASTRUCTURE_TIMEOUT_SECONDS`, `INFRASTRUCTURE_CACHE_TTL_SECONDS`,
  `INFRASTRUCTURE_MAX_IPS` (behavioral caps for a single scan).

## 10. Dashboard presentation

- A new `InfrastructureCard` rendered inside the existing `ModuleGrid` via the
  per-module renderer hook (the same mechanism that injects
  `ThreatIntelCard`): `DashboardPage` registers
  `renderers={{ threatintel: ThreatIntelCard, infrastructure: InfrastructureCard }}`.
- Content: resolved IP(s), ASN badge (`AS15169`), hosting organization,
  country + region, provider/source line with `timestamp`, and a fixed
  informational disclaimer ("Approximate location of the hosting network; not
  an indication of who operates the site or where any person is located").
- `Unavailable` state: provider slug + reason code (existing
  `unavailable` reason vocabulary), no IP shown unless the DNS module resolved
  one (the IP itself is already public knowledge from DNS details).
- No map. No coordinates. No new dependency.

## 11. Report presentation

- Same `InfrastructureCard` rendered on `ReportPage` (registered in the same
  `renderers` map), placed beside the Threat Intelligence card / within
  Security Modules grid for parity with Dashboard.
- Exports: CSV gets an `Infrastructure` block (key/value rows like the
  threatintel block); PDF gets an "Infrastructure" table with the same fields.
- Historical scans: the card renders from the stored `details` snapshot; if an
  older scan has no `infrastructure` module, the card is simply absent
  (ReportPage already guards on module existence).

## 12. Error / unavailable-provider behavior

- Provider missing key / disabled → `status: "unavailable"`,
  `reason: "missing_api_key"`, module score 100, confidence 100, no findings.
- Timeout/network error → `unavailable` with `timeout`/`network` reason; same
  zero-penalty treatment.
- HTTP 429/401/403/5xx → `rate_limited` / `unauthorized` / `server_error`;
  same treatment.
- Malformed/empty payload → `bad_response`/`no_analysis`; same treatment.
- Domain does not resolve → module reports `unavailable`
  (`reason: "invalid_target"`-style), informational only.
- **Rule (house law, already enforced for WHOIS and threat intel):** a failed
  lookup is a *missing data point*, never a verdict, never a penalized module.
- No retries: one attempt per IP per scan (v1 precedent: virus_total never
  retries).

## 13. Security considerations

- Provider API key: env-only, never logged, never echoed into responses
  (existing secret hygiene rules apply; failures log exception *classes*, not
  payloads).
- Provider responses are untrusted input: validate/normalize inside the
  adapter; bound all string lengths (e.g. 80-char truncation like
  `_MAX_EVIDENCE_LEN` in the VirusTotal adapter).
- Never infer malice from hosting context: a site hosted in country X or on
  ASN Y is **not** a security finding. The card forbids severity-bearing
  language.
- Output caching bounded and keyed by IP only; no user-controlled cache keys.
- Keep v1 guards intact: any future outbound host contact still goes through
  `app/utils/networking.validate_public_host`; the infrastructure provider
  endpoint itself is a fixed, trusted, config-provided URL (see §15).

## 14. Privacy considerations

- Displayed data is public routing information (ASN, CIDR, country) about IPs
  the DNS module already publishes. No new personal-data surface for the
  scanned domain.
- Labeling discipline in UI copy and any future exports:
  - **Target infrastructure location** — the hosting network for the scanned
    domain's resolved IPs.
  - **Threat infrastructure location** — an IP/network associated with a
    threat-intelligence finding (evidence-linked; only if a future release
    surfaces threat IPs).
  - **Attacker location** — **never claimed.** Ordinary IP geolocation does
    not establish a person's physical location or identity. This prohibition
    is documented here and must be repeated in the card's static disclaimer.
- No device/owner inference; no "street-level" claims; region shown only when
  provider-labeled.

## 15. SSRF considerations

- The provider endpoint is a fixed, administrator-configured URL; the value
  sent to it is a **validated IP literal** derived from DNS resolution of the
  scan target — never an arbitrary user-supplied host. SSRF surface therefore
  does not materially change.
- Input validation before any provider contact: the target host is already
  validated as a public host by the v1 pipeline (URL validation + DNS module +
  `validate_public_host` for any direct connection); the infrastructure module
  must additionally reject private/reserved/loopback/link-local/CGNAT resolved
  addresses (reuse `_is_private_address` logic in `app/utils/networking.py`)
  before sending them to the provider.
- Rate/behavior caps per scan (max IPs looked up) keep user-paced scanning
  behavior identical to v1.

## 16. Rate-limit considerations

- One provider request per resolved IP, capped per scan
  (`INFRASTRUCTURE_MAX_IPS`, default e.g. 3 — DNS module A/AAAA sets are small),
  with a per-domain de-duplicate.
- Cache by IP (see §8) — popular CDN ranges (e.g. 142.250.x.x) dominate real
  scans, so cache hits keep provider load near zero in steady state.
- Timeouts default ~5 s, provider-paced; failures short-TTL cached to avoid
  retry storms.
- Document per-provider free-tier quotas in `backend/README.md` style when a
  provider is selected (v1 precedent: VirusTotal free tier ≈ 4 req/min,
  500 req/day).

## 17. Provider failure behavior

- If the provider is down or misconfigured, scans **must still complete**:
  the infrastructure module is one isolated `ModuleResult` among eleven-plus;
  every failure path returns `unavailable` with zero penalty (ScanManager
  already wraps module exceptions into error results as a backstop).
- Deployment implication: the gate to release v1.1 is `INFRASTRUCTURE_ENABLED`
  defaulting to **off**; existing deployments behave identically to v1 unless
  an operator opts in with a key.

## 18. Why the feature does not affect scoring

- The Risk Engine is driven exclusively by `MODULE_WEIGHTS`
  (`backend/app/risk_engine/weights.py`); the scorer skips any module without a
  weight and re-normalizes over contributors.
- The infrastructure module is deliberately **absent from `MODULE_WEIGHTS`**,
  so it contributes neither to `trust_score` nor to aggregate `confidence`, and
  cannot move the verdict or any existing module's penalty.
- `ModuleResult` fields returned are score 100 / confidence 100 in all states;
  findings list stays empty or `info`-severity only — and the frontend renders
  the card from `details` only, never from score fields.
- If a future release ever introduces a *specific* security signal (e.g. a
  maintained "known-abuse ASN" feed), it must be implemented as a separate
  weighted signal with its own rule set and explicit review — not implied by
  this informational card.

## 19. Testing strategy

Mirror the existing pytest style (injected adapters/transport mocks,
`httpx.MockTransport`, no real network). Required cases:

**Module / enrichment**
- Valid IP enrichment: full profile (ASN, org, country, region) lands in
  `details`, source + timestamp set.
- Provider available → `status: "available"`.
- Provider unavailable (missing key) → `unavailable` + `missing_api_key`.
- Provider timeout → `unavailable` + `timeout`.
- Provider HTTP 429/401/5xx → mapped reason codes.
- Malformed provider response (bad JSON, wrong shape, unknown fields) →
  `bad_response`, values normalized, nothing crashes.
- Domain does not resolve → module `unavailable`, no provider call.
- Multiple IPs (A + AAAA) → bounded lookups, de-dupe, cap enforced.
- Missing ASN / missing country / missing region → field `None`, module still
  `ok` (no finding).
- IPv6 literal handling.

**Cache**
- Cache hit: second scan performs no provider call (mock counts calls).
- Cache miss → one provider call.
- Expired entry → re-queried (TTL injection).
- Provider failure cache: short TTL, not served as `available`.

**Scoring isolation**
- Byte-identical `AnalysisResponse` (minus the added module's JSON) with and
  without infrastructure enabled — asserts zero impact on
  trust_score/confidence/verdict/summary and on all other module results.
- Findings list never gains severity-bearing entries from the module.

**Frontend**
- InfrastructureCard renders correct fields from `details`.
- Correct rendering on Dashboard and Report pages (component tests).
- Unavailable state shows reason, no fabricated location.
- Correct labeling: fixed disclaimer present; no "attacker" string anywhere.

**Contracts/regression**
- Full v1 test suite remains green (no behavior regression, §compat).
- CSV/PDF export blocks render infrastructure rows.

## 20. Acceptance criteria

1. `docs` and implementation match: InfrastructureProfile exactly per §7.
2. Scanning a domain with the feature enabled returns an `infrastructure`
   module result with ASN/org/country/region when the provider answers.
3. Provider failure (any kind) never changes trust_score, confidence, verdict,
   summary, or any other module's result; scans still complete.
4. Card renders on Dashboard and Report with source/timestamp and the static
   geographical-approximation disclaimer.
5. Provider is swappable via one adapter boundary — no other code change
   required for a different provider.
6. Caching by IP proven by tests (no provider call on cache hit within TTL).
7. Export blocks (CSV/PDF) present; JSON includes the module by construction.
8. Feature disabled by default; no v1 test regressions; v1 commit untouched.

## 21. Implementation phases

1. **Phase 0 — design freeze:** this document (complete).
2. **Phase 1 — provider decision:** evaluate candidate providers against the
   §6 contract (licensing, free tier, country/region reliability, key
   handling). No code changes yet.
3. **Phase 2 — backend skeleton:** `modules/infrastructure/` models + service
   + adapter interface + registry entry; provider disabled by default;
   scoring isolation tests.
4. **Phase 3 — provider adapter:** concrete adapter for the chosen provider
   (env-keyed, timeout, reason taxonomy) + mocked tests.
5. **Phase 4 — caching:** keyed cache per §8 + cache tests.
6. **Phase 5 — exports & endpoint:** CSV/PDF blocks; optional
   `/infrastructure/{domain}` route.
7. **Phase 6 — frontend:** `InfrastructureCard`, renderer registrations on
   Dashboard and Report, formatter summary case.
8. **Phase 7 — release hardening:** full suite, lint/build, Docker verification,
   README/env documentation, v1.1 commit.

Phase 1 must complete before Phase 3: the adapter contract in Phase 2 keeps
the chosen provider isolated.

## 23. Dependencies likely required

- **Backend:** exactly one provider SDK — or none, if the chosen provider
  exposes a JSON REST API consumable with the already-installed `httpx`
  (preferred: zero new Python dependencies). Candidate providers (evaluation
  deferred to Phase 1; none selected, none installed):
  - VirusTotal v3 `ip_addresses/{id}` — reuses the existing key/quota path but
    shares the tight VirusTotal free rate limit.
  - Dedicated ASN/geo providers (e.g. ipinfo, ip-api, MaxMind GeoIP2) — own
    key/quotas; license terms must permit informational display of
    country/region.
- **Frontend:** none. The card uses existing `Card`/`Badge` components and CSS
  modules.
- **Explicitly excluded:** no map SDK, no tile provider, no new runtime
  frontend packages.

## 24. Future map considerations

Not in v1.1. If a map is ever considered (v1.2+):

- It requires the backend to emit **licensed coordinates** (a provider decision
  with license review) — country-only data cannot justify a map.
- It requires a frontend dependency (e.g. Leaflet or MapLibre) and possibly
  tile-provider terms/keys; both are new attack/consent surfaces.
- Data still cannot support "attacker location" claims; map labeling must use
  the target/threat-infrastructure vocabulary.
- Recommended order: infrastructure card ships first and proves
  data-quality/user value; only then evaluate map cost.

## Final section

### v1.1 recommendation

**Build it, deferred to v1.1 — as specified here and no larger.** The feature
is genuinely useful analyst context and cheap to add because v1 already
resolves and persists the IPs. Ship v1 first; do not reopen the v1 branch for
this feature.

### Implementation order

1. Publish CyberShield **v1** (repository creation → push `9b0c31b` →
   portfolio polish).
2. Phase 0–1 of this spec (freeze design, evaluate providers) — can run in
   parallel with v1 publishing.
3. Phases 2–7 tracked on the v1.1 branch only.
4. v1.1 release with `INFRASTRUCTURE_ENABLED=false` default and full v1
   regression suite green.

### Definition of done

- All §20 acceptance criteria pass.
- Full v1 backend suite (278 tests at v1) green plus new infrastructure/cache/
  isolation/frontend tests.
- Frontend lint + build clean; Docker build/runtime re-verified.
- Trust Score, verdict, confidence and finding severities byte-identical with
  the feature on vs off.
- Documentation (README, `.env.example`, this spec) updated; no map, no
  "attacker location" copy anywhere.

### Explicit v1 compatibility statement

**No v1 behavior should regress.** CyberShield v1 remains unchanged at commit
`9b0c31b` (`feat: release CyberShield v1`). All v1.1 work happens additively on
top of that commit — new module, new card, optional env keys — with the feature
opt-in and off by default. Existing scans, stored reports, exports, API shapes
and Trust Score semantics are untouched by this design. This document changes
nothing; it only records the plan.
